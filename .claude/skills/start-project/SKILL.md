# Запуск нового проекта

Идея: $ARGUMENTS

## Этап 1. Требования (файлы не создавать)

1. Выполни `Get-Location` и назови папку, в которой будет проект. Посмотри её содержимое и `git status` (если это репозиторий). Если папка не пуста или есть незакоммиченные изменения — перечисли их и спроси, продолжать ли здесь.
2. Задай вопросы одним сообщением (пропусти то, на что уже ответила идея):
   - цель проекта — какую задачу он решает;
   - пользователи — кто и как будет им пользоваться;
   - основные функции — 3–7 пунктов для первой версии;
   - стек — язык, runtime, фреймворки (или «на твоё усмотрение»);
   - ограничения — зависимости, окружение, сроки, хранение данных, безопасность, язык интерфейса.
3. Остановись и дождись ответов. Не додумывай важное: при неясности переспроси.

## Этап 2. Спецификация и план (файлы не создавать)

4. Сформируй краткую спецификацию:
   - цель и пользователи (1–2 предложения);
   - функции первой версии;
   - что сознательно не входит в первую версию;
   - критерии готовности — проверяемые пункты.
5. Предложи минимальную структуру — дерево файлов с назначением каждого. Правила:
   - только то, что нужно для первой версии; без пустых папок «на будущее»;
   - без лишних инструментов (сборщиков, линтеров, CI, Docker, фреймворков), если их не требуют стек или ограничения;
   - `README.md` — если проектом будет кто-то пользоваться или его запускать (почти всегда): что это, как запустить, как тестировать;
   - `CLAUDE.md` — если проект будет развиваться с Claude Code: стек, команды запуска и тестов, правила архитектуры и безопасности;
   - `.gitignore` — если есть git или генерируемые файлы, зависимости, локальные настройки; всегда включай `.env*`, ключи и сертификаты (`*.pem`, `*.key`);
   - тесты — если есть логика, которую можно проверить; встроенным раннером стека, когда он есть.
6. Проверка секретов — опиши в плане:
   - секреты не пишутся в код, конфиги, README и CLAUDE.md;
   - если нужны ключи — только через переменные окружения и `.env.example` с пустыми значениями;
   - `.gitignore` исключает `.env*` (кроме `.env.example`), ключи и сертификаты.
7. Покажи: спецификацию, критерии готовности, дерево файлов, команды запуска и тестов, план проверки.
8. Остановись и дождись явного подтверждения. Неоднозначный ответ — не подтверждение: переспроси. Правки плана — покажи обновлённый план и снова жди подтверждения.

## Этап 3. Создание и проверка

9. Создай только согласованные файлы. Если понадобилось выйти за план — остановись и спроси.
10. Если git-репозитория нет — спроси, нужен ли `git init`, и выполни только после согласия.
11. Проверь секреты: поищи в созданных файлах похожие на секреты строки (`password`, `secret`, `token`, `api_key`, `BEGIN .* PRIVATE KEY`) и убедись, что `.gitignore` их исключает. Сообщи результат.
12. Запусти тесты (если они есть) и покажи их вывод полностью. Если тесты упали — исправь в рамках плана или сообщи честно.
13. Покажи `git status` и `git diff` (для новых неотслеживаемых файлов — `git add -N .` перед `git diff`, либо выведи их содержимое), список созданных файлов и проверь критерии готовности по пунктам.

## Всегда

14. Не создавай commit и не делай push без отдельного явного разрешения.
15. Не меняй глобальные настройки Git (`--global`, `--system`) и не работай за пределами папки проекта.
16. Не читай, не создавай и не записывай секреты: `.env` с реальными значениями, ключи, сертификаты, пароли и токены.
17. Не устанавливай зависимости и глобальные инструменты без согласования в плане.
